# Validate a research release

Use this workflow when preparing or reviewing a standalone research/code bundle. It checks packaging, not scientific truth or permission to publish. Keep changes in a staging area until the required content review is complete and publication is authorized.

1. Have an explicitly identified, accountable editorial reviewer, human or agent as permitted by task authorization, review each proposed public file and its intended audience. Agent review is not human approval. Exclude private coordination/handoff artifacts and unrelated content. Do not classify all review reports or skills as private: purpose, provenance, and reviewed content matter. Filename heuristics and category labels cannot prove privacy. Newly written public instructions are preferable to copying internal material.
2. Prepare a separately reviewed JSON manifest with exact file paths and SHA-256 hashes of the final bytes. Keep truthful evidence of reviewer identity and type, reviewed audience, outcome, and the exact paths/hashes reviewed, as described in README.md. Record an approved public category per file; record editorial approval only after it actually occurs. Changed bytes need renewed review and hashes. Freeze the manifest separately from the ZIP. A manifest generated from an unreviewed archive is not an independent trust anchor.
3. Declare supporting local files explicitly, including documentation consumed by tests. Keep large model weights or other intentionally external dependencies external, with their source and immutable revision/digest. Do not download or silently bundle them. Review pins manually; the validator checks declaration presence, not remote authenticity.
4. Validate the archive with scripts/validate_release.py and the schema/example in README.md. The helper accepts ZIPs containing only regular files, checks the exact allowlist and hashes, rejects unsafe paths, links and duplicates, and limits uncompressed size. Directory entries must be omitted when packaging.
5. After reviewing the declared Python test code and confirming execution is authorized, use --run-tests. Editorial approval alone establishes neither test-code trust nor execution authorization. This writes verified bytes into a new temporary directory and runs tests there, not in the populated source checkout. The helper does not provide an OS/network security sandbox. Do not execute untrusted archive code with this helper. Review and establish trust first; additional OS-level isolation or offline execution must be provisioned externally. Do not run installations, experiments or downloads merely to obtain a passing packaging check.
6. Report packaging status and test status separately. A missing bundled requirement blocks validation. Tests requiring declared external dependencies remain explicitly unrun. A clean synthetic/unit-test run does not establish full scientific reproduction. Report what ran, what did not, command, environment, exit status, and remaining editorial/scientific review. Verify publication permission separately: neither review nor passing tests grants it. Follow all governing confirmation requirements, including any required action-time approval or handoff. This skill and its approval fields grant no authorization, override no denial, and prove no privacy guarantee. Validation itself does not publish.

Use the included fixture suite to check validator changes. When an actual release fails, fix the source packaging/dependency declarations, rebuild, review changed content and regenerate hashes, then rerun against the new standalone archive. Never remove a needed dependency or weaken a test merely to turn the gate green.
